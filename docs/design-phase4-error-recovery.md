## 0. 一句话概括现状

**现在任何一条流出错，整个传输立刻判死刑，之前传的几十 GB 全部作废。**

打个比方：搬家公司的卡车在半路爆胎，司机不换备胎、也不换车，而是宣布"这次搬家失败"，
把家具原样拉回出发地——明天你再叫一次车，从第一件家具重新开始搬。

本文要定的就是：**什么情况该换备胎、什么情况该换车、什么情况确实该放弃**。

## 1. 现状基线（已核对代码）

| 事实 | 位置 | 影响 |
|---|---|---|
| 每个 chunk **新建一条 TCP 连接** | `transfer.rs:1086` 在 while 内 | 一个 1GB 文件 / 16MB = 64 次握手；连接建立失败是主要失败源 |
| 接收端 `serve_data_stream` **处理一帧就返回** | `transfer.rs:501-514` | 连接无法复用，只能一帧一连接 |
| `send_chunk` 等 ACK **60 秒**，期间不检查取消 | `transfer.rs:1172` | 点取消要等 60s 才有反应（N9） |
| 任一 worker 出错 → **整体 Failed，零重试** | `transfer.rs:1124-1144` | 瞬时抖动直接毁掉整次传输 |
| `ReceiveSlot` **已有** `chunk_size` 和 `received_chunks` 位图 | `storage.rs:32-38` | 好消息：重试所需的"哪些块到了"的信息已经存在，**不用新建数据结构** |
| 取消信号用 `watch::channel(false)` | `transfer.rs:775` | 已有基础设施 |

**关键观察**：`received_chunks` 位图已经在了。这意味着"重传未完成的块"在数据层面
是现成的，缺的只是把它接进失败处理路径。

## 2. 失败模式清单

按"能不能靠重来一次解决"分成三类。这个分类是整个设计的地基。

### A 类：可重试（瞬时故障，重来大概率成功）

| 失败 | 怎么检测到 | 恢复动作 |
|---|---|---|
| 连接建立失败（对端未监听 / 端口未开 / 瞬时拒绝） | `TcpStream::connect` 返回 Err | 退避后重连，重试 N 次 |
| 传输中连接断开（RST / 意外 EOF） | `write_all` 或 `read_until` 返回 Err | 重开连接，从位图里下一个未确认块继续 |
| chunk ACK 超时（对端卡住 / 网络抖动） | `timeout` 触发 | 同上（注意：此时该块**可能已经落盘**，重发是幂等的） |
| 对端主循环短暂繁忙导致 ACK 慢 | 同上 | 同上 |

### B 类：重试无用，必须放弃（重来还是一样的结果）

| 失败 | 为什么不能重试 |
|---|---|
| **整文件 sha256 校验失败** | 说明数据本身不对。重传一遍很可能拿到同样的错数据，白白浪费带宽。应直接 Failed 并**保留 .part 供排查** |
| **磁盘写满 / 无写权限** | 重试只会再失败一次，还可能把错误刷屏 |
| **chunk_id 不匹配 / 协议解析失败** | 这是 bug 或版本不兼容的信号，重试掩盖问题 |
| **文件槽位不存在**（对端已取消或已清理） | 对端已经不想收了 |

### C 类：人为终止（不是"故障"，是"指令"）

| 场景 | 处理 |
|---|---|
| 本端用户取消 | 立即停，不等 ACK 超时（N9） |
| 对端用户取消（跨机 `POST /api/cancel/:file_id`） | 立即停，标记 Canceled |
| 接收方 60s 未决策 | 发送方超时放弃 |

**C 类必须能打断 A 类的重试**——这是最容易写错的地方：
一个正在重试的传输，用户点了取消，结果界面显示"重试中，无法取消"。

## 3. 恢复策略分四层

```
L3  跨重启续传   进程重启后接着传  ── 需要元数据落盘，成本高
L2  连接级重试   重开连接，从未确认块继续  ── 核心，必做
L1  块级重试     同一连接内重发当前块      ── 简单，先做
L0  连接复用     一条连接传完整条流        ── 消除大部分失败源，必做
```

**L0 连接复用是本阶段性价比最高的一项**。
现在 64 个 chunk 要建 64 次连接，每次都可能失败；改成一条长连接后，
失败机会直接降到个位数。而且它顺带解决性能问题（省 64 次握手）。

---

## 4. 一个重要的建议：把「重试」和「续传」拆开

方案把 4.0（chunk_size 协商）和 4.1-4.3（重试）放一起，看起来是同一件事。
但我核对代码后认为它们该分开处理：

### 4.0 chunk_size 协商（N2）—— **必须做，这是正确性 bug**

不是"可靠性增强"，是**现在就会静默损坏数据**：

```
发送方 A 本地配置 chunk_size=16MB  →  切成 16MB 的块发出去
接收方 B 本地配置 chunk_size=64MB  →  按 64MB 的槽位建 .part，按 64MB 算偏移
                                      ↓
                       写进去的位置全错，但每个块都"成功"落盘
                                      ↓
                        只有最后整文件 sha256 能发现，为时已晚
```

**修法**：`HttpOffer` 带上 `chunk_size`，接收方建槽时**用 offer 里的值**，不用本地配置。
约 10 行代码，但必须做，否则后面所有可靠性工作都建在错误的基础上。

### 重试（4.1-4.4）—— **建议本阶段做，收益大**

重试所需的位图已经有了（见 §1），主要工作是把它接进失败路径。
这能解决 90% 的实际故障（网络抖动、连接被路由器掐断）。

### 跨重启续传（N3）—— **建议拆出来延后**

N3 要解决的是"进程重启后接着传"，它需要：
1. 把槽位元数据（chunk_size、位图、原 file_id）落盘成 `file_id.meta`
2. 启动时扫描 receive_dir，认领未完成的 .part
3. 设计 .part 的过期与清理策略（否则磁盘会堆满垃圾）
4. 解决"发送方怎么知道旧 file_id"——需要 B 侧按 (name, size, mtime) 匹配后回传

第 4 点还引出 `source_mtime` 的跨平台精度问题（Q6：FAT32 只有 2 秒精度）。

**建议延后的理由**：局域网传输通常几分钟内完成，进程重启的概率远低于网络抖动；
而落盘元数据 + 启动扫描 + 过期清理是**另一个量级的工作量**，还会引入新的状态不一致问题。

如果采纳这个建议，阶段 4 的范围变成：**4.0 + 4.1~4.4 + 4.5**，
N3 整体挪到后续阶段（连同 Q6 的 mtime 难题一起解决）。

## 5. 状态机

```
                 ┌──────────┐
                 │ Pending  │
                 └────┬─────┘
                      │ POST /api/send
                      ▼
    ┌──────────► Transferring ◄──────────┐
    │           │             │           │
    │           │  chunk 失败 │           │ 重连成功
    │           ▼             │           │
    │      ┌─────────┐        │      ┌────┴────┐
    │      │ Retrying│────────┼─────►│Reconnect│
    │      └────┬────┘ 耗尽   │      └─────────┘
    │           │             │
    │           ▼             ▼ 全部 chunk 完成
    │        Failed      Verifying（等 sha256）
    │                         │
    │                    ┌────┴────┐
    │                    ▼         ▼
    │               Completed   Failed（校验不过）
    │
    └── 用户取消 / 对端取消 ──► Canceled
              （任何状态都可进入）
```

**设计要点**：`Retrying` 和 `Reconnect` 都必须能被取消信号打断。
实现方式：`send_chunk` 里的 ACK 等待改成
`tokio::select! { 等ACK, 等cancel_rx.changed() }`（这也是 N9 的解法）。

## 6. 具体参数（建议值，需拍板）

| 参数 | 现状 | 建议 | 理由 |
|---|---|---|---|
| chunk ACK 超时 | 60s | **20s** | 局域网内一个 16MB 块落盘不该超过 20s；60s 意味着用户点取消要等一分钟 |
| 单块重试次数 | 0 | **3** | 再多就是拿用户的带宽赌运气 |
| 重试退避 | 无 | **0 / 200ms / 500ms** | 局域网不需要长退避，长退避只会让传输显得卡死 |
| 连接建立重试 | 0 | **3 次，间隔 500ms** | 覆盖"对端 daemon 刚启动还没监听"这种场景 |
| 整次传输的总重试预算 | 无 | **不限次数，但连续失败 10 块则整体放弃** | 连续失败说明不是抖动，是对端出了问题 |

## 7. 存疑点的裁决

| # | 存疑 | 裁决 |
|---|---|---|
| Q2 | 续传复用 file_id 会覆盖 `progress_cache` 里的旧条目 | **接受覆盖**。续传本就是同一文件的延续，UI 上显示一条比两条合理 |
| Q6 | `source_mtime` 跨平台精度（FAT32 2 秒精度） | **若采纳 §4 建议（续传延后），本阶段不触及**。将来做时：用 `(size, mtime±2s)` 双条件匹配，宁可匹不上走全新传输，也不要续错文件 |
| Q7 | 同一对端同时发两个相同文件，抢同一 `resume_file_id` | B 侧对**活跃槽位拒绝续传**，走全新传输落到 `name (1).ext`。简单可靠，不引入锁 |

## 8. 测试清单

| # | 场景 | 验证点 |
|---|---|---|
| 1 | 多块小文件（调小 chunk_size） | 连接复用后多块走同一条连接，不回归 |
| 2 | 传输中途 drop 连接 | 自动重试并成功完成 |
| 3 | **两端 chunk_size 配置不同** | sha256 仍与源文件一致（**N2 回归，最重要的一条**） |
| 4 | 传输中点取消 | 两侧立即停止，不出现"取消后还在传" |
| 5 | 对端进程被杀 | 发送方重试耗尽后 Failed，不无限重试 |
| 6 | 接收目录磁盘满 | 写盘失败立即 Failed，不做无谓重试 |
| 7 | 接收目录已有同名文件 | 自动改名为 `name (1).ext`，不覆盖 |

第 3 条是重中之重——它是唯一能在代码合入前抓住"静默数据损坏"的测试。

## 9. 明确不做（避免范围蔓延）

- 跨重启续传（N3 整体，见 §4）
- 发送窗口 / 滑动窗口（保持停等，方案已定死）
- 自适应 chunk_size（按网络状况动态调整）
- 断点续传的 UI 入口（本阶段无用户可见的续传功能）

## 10. 需要你拍板的三件事

1. **续传拆不拆？** 我建议把 N3（跨重启续传）从阶段 4 挪走，本阶段只做
   `4.0 + 4.1~4.5`。这样阶段 4 能更快落地，且避开 mtime 精度这个坑。
   如果你希望一次做完，我也可以按原方案做，但工作量会显著增加。

2. **重试参数**（§6 表格）是否认可？特别是 ACK 超时从 60s 降到 20s——
   在极端慢的设备上（比如老安卓机写 eMMC），20s 可能不够，需要你判断目标设备。

3. **连接复用（L0）要不要做？** 方案里是 4.1/4.2 两项，属于性能优化。
   我强烈建议做——它同时消除大部分失败源，是"可靠性"和"性能"的公约数。
