## 评审结论（2026-09-05 定案）

| 项 | 定案 | 备注 |
|---|---|---|
| 阶段范围 | **拆**：只做 4.0 + 4.1~4.5，跨重启续传（N3）延后 | 见 §4 |

## 0. 一句话概括现状

**现在任何一条流出错，整个传输立刻判死刑，之前传的几十 GB 全部作废。**

打个比方：搬家公司的卡车在半路爆胎，司机不换备胎、也不换车，而是宣布"这次搬家失败"，
把家具原样拉回出发地——明天你再叫一次车，从第一件家具重新开始搬。

本文要定的就是：**什么情况该换备胎、什么情况该换车、什么情况确实该放弃**。

## 1. 现状基线（已核对代码）

| 事实 | 位置 | 影响 |
|---|---|---|
| 每个 chunk **新建一条 TCP 连接** | `transfer.rs:1086` 在 while 内 | 一个 1GB 文件 / 16MB = 64 次握手；连接建立失败是主要失败源 |
| 接收端 `serve_data_stream` **处理一帧就返回** | `transfer.rs:501-514` | 连接无法复用，只能一帧一连接 |
| `send_chunk` 等 ACK **60 秒**，期间不检查取消 | `transfer.rs:1172` | 点取消要等 60s 才有反应（N9） |
| 任一 worker 出错 → **整体 Failed，零重试** | `transfer.rs:1124-1144` | 瞬时抖动直接毁掉整次传输 |
| `ReceiveSlot` **已有** `chunk_size` 和 `received_chunks` 位图 | `storage.rs:32-38` | 好消息：重试所需的"哪些块到了"的信息已经存在，**不用新建数据结构** |
| 取消信号用 `watch::channel(false)` | `transfer.rs:775` | 已有基础设施 |

**关键观察**：`received_chunks` 位图已经在了。这意味着"重传未完成的块"在数据层面
是现成的，缺的只是把它接进失败处理路径。

## 2. 失败模式清单

按"能不能靠重来一次解决"分成三类。这个分类是整个设计的地基。

### A 类：可重试（瞬时故障，重来大概率成功）

| 失败 | 怎么检测到 | 恢复动作 |
|---|---|---|
| 连接建立失败（对端未监听 / 端口未开 / 瞬时拒绝） | `TcpStream::connect` 返回 Err | 退避后重连，重试 N 次 |
| 传输中连接断开（RST / 意外 EOF） | `write_all` 或 `read_until` 返回 Err | 重开连接，从位图里下一个未确认块继续 |
| chunk ACK 超时（对端卡住 / 网络抖动） | `timeout` 触发 | 同上（注意：此时该块**可能已经落盘**，重发是幂等的） |
| 对端主循环短暂繁忙导致 ACK 慢 | 同上 | 同上 |

### B 类：重试无用，必须放弃（重来还是一样的结果）

| 失败 | 为什么不能重试 |
|---|---|
| **整文件 sha256 校验失败** | 说明数据本身不对。重传一遍很可能拿到同样的错数据，白白浪费带宽。应直接 Failed 并**保留 .part 供排查** |
| **磁盘写满 / 无写权限** | 重试只会再失败一次，还可能把错误刷屏 |
| **chunk_id 不匹配 / 协议解析失败** | 这是 bug 或版本不兼容的信号，重试掩盖问题 |
| **文件槽位不存在**（对端已取消或已清理） | 对端已经不想收了 |

### C 类：人为终止（不是"故障"，是"指令"）

| 场景 | 处理 |
|---|---|
| 本端用户取消 | 立即停，不等 ACK 超时（N9） |
| 对端用户取消（跨机 `POST /api/cancel/:file_id`） | 立即停，标记 Canceled |
| 接收方 60s 未决策 | 发送方超时放弃 |

**C 类必须能打断 A 类的重试**——这是最容易写错的地方：
一个正在重试的传输，用户点了取消，结果界面显示"重试中，无法取消"。

## 3. 恢复策略分四层

```
L3  跨重启续传   进程重启后接着传  ── 需要元数据落盘，成本高
L2  连接级重试   重开连接，从未确认块继续  ── 本阶段不做（见下）
L1  块级重试     重新建连接重发当前块      ── 本阶段做，即 4.3
L0  连接复用     一条连接传完整条流        ── 本阶段**不做**，见 §10.3
```

**关于 L0 连接复用**：本阶段**不做**，理由见 §10.3。
这里保留四层的划分，是为了将来要做时能直接对上号。

顺带记一个容易搞错的数字：并行流数默认是 `min(CPU核数, 8)`（`lib.rs:71`），
不是 2。所以连接复用的收益是「64 次建连 → 8 次建连」（8 倍），
而不是「→ 2 次」（32 倍）。
（我一开始就是照着测试代码里的 2 流举例，把测试参数当成了默认配置，
在讨论中算成了 2 次，已更正。）

## 4. 定案：把「重试」和「续传」拆开

方案把 4.0（chunk_size 协商）和 4.1-4.3（重试）放一起，看起来是同一件事。
核对代码后确认该分开处理，评审已采纳。

### 4.0 chunk_size 协商（N2）—— **必须做，这是正确性 bug**

不是"可靠性增强"，是**现在就会静默损坏数据**：

```
发送方 A 本地配置 chunk_size=16MB  →  切成 16MB 的块发出去
接收方 B 本地配置 chunk_size=64MB  →  按 64MB 的槽位建 .part，按 64MB 算偏移
                                      ↓
                       写进去的位置全错，但每个块都"成功"落盘
                                      ↓
                        只有最后整文件 sha256 能发现，为时已晚
```

**修法**：`HttpOffer` 带上 `chunk_size`，接收方建槽时**用 offer 里的值**，不用本地配置。
约 10 行代码，但必须做，否则后面所有可靠性工作都建在错误的基础上。

### 重试（4.1-4.4）—— **本阶段做**

重试所需的位图已经有了（见 §1），主要工作是把它接进失败路径。
这能解决 90% 的实际故障（网络抖动、连接被路由器掐断）。

### 跨重启续传（N3）—— **定案延后**

N3 要解决的是"进程重启后接着传"，它需要：
1. 把槽位元数据（chunk_size、位图、原 file_id）落盘成 `file_id.meta`
2. 启动时扫描 receive_dir，认领未完成的 .part
3. 设计 .part 的过期与清理策略（否则磁盘会堆满垃圾）
4. 解决"发送方怎么知道旧 file_id"——需要 B 侧按 (name, size, mtime) 匹配后回传

**延后的理由**：局域网传输通常几分钟内完成，进程重启的概率远低于网络抖动；
而落盘元数据 + 启动扫描 + 过期清理是**另一个量级的工作量**，还会引入新的状态不一致问题。

### 4.1 「留字段」做实 —— 拆，但将来加回来不用改线格式

> **编号提醒（2026-09-06 补）**：本节的 4.1 是「留字段」，**不是**最初方案里的
> 「连接复用」。最初方案的 4.1 / 4.2（连接复用）已在 2026-09-05 复审后移出本阶段
> （见 §10.3），编号空出后本节沿用了 4.1。因此本阶段**没有 4.2**。
> 4.0 / 4.3 / 4.4 / 4.5 的编号在两套方案里含义一致，不受影响。

拆不等于不留后路。现在定死两件事，将来做 N3 时**只填数据、不改格式**：

**① `HttpOffer` 的 `chunk_size`** —— 4.0 会加上，本次就定型。
接收方一律用它建槽，本地配置退化为"仅在本机发起 offer 时作为默认值"。

**② `.part` 槽位元数据格式现在定型**。将来 `<file_id>.meta` 写成下面这个 JSON，
字段只增不改（新增字段给默认值，旧 meta 仍能读）：

```json
{
  "version": 1,
  "file_id": "uuid",
  "file_name": "a.mp4",
  "file_size": 10737418240,
  "chunk_size": 16777216,
  "chunk_count": 640,
  "sha256": null,
  "bitmap": "base64(bit-packed, LSB-first)",
  "created_at": 1757000000,
  "peer_id": "dev-1",
  "source_mtime": null
}
```

几点说明：
- `bitmap` 用位打包而不是布尔数组：640 个块 = 80 字节，布尔 JSON 数组要 3KB 以上。
- `sha256` / `source_mtime` 允许为 null（deferred 补发、以及将来才启用 mtime 匹配）。
- `version` 从 1 开始：将来格式变更时，读到不认识的 version 就**丢弃并走全新传输**，
  好过按错误格式解析出一堆错位数据。
- 本阶段**不写这个文件**（续传延后），但结构体定义和序列化代码先落地，
  并用单元测试锁住格式——避免将来真要做时，发现当初定的结构有坑。

## 5. 状态机

```
                 ┌──────────┐
                 │ Pending  │
                 └────┬─────┘
                      │ POST /api/send
                      ▼
    ┌──────────► Transferring ◄──────────┐
    │           │             │           │
    │           │  chunk 失败 │           │ 重连成功
    │           ▼             │           │
    │      ┌─────────┐        │      ┌────┴────┐
    │      │ Retrying│────────┼─────►│Reconnect│
    │      └────┬────┘ 耗尽   │      └─────────┘
    │           │             │
    │           ▼             ▼ 全部 chunk 完成
    │        Failed      Verifying（等 sha256）
    │                         │
    │                    ┌────┴────┐
    │                    ▼         ▼
    │               Completed   Failed（校验不过）
    │
    └── 用户取消 / 对端取消 ──► Canceled
              （任何状态都可进入）
```

**设计要点**：`Retrying` 和 `Reconnect` 都必须能被取消信号打断。
实现方式：`send_chunk` 里的 ACK 等待改成
`tokio::select! { 等ACK, 等cancel_rx.changed() }`（这也是 N9 的解法）。

## 6. 具体参数（已定案）

### 6.1 最重要的一条：取消要立刻生效，不靠缩短超时

原本我把注意力放在"ACK 超时 60s 太长"上，评审时纠正了这个偏差——

> 超时值不是最大的问题，等待 ACK 期间不 `select!` `cancel_rx` 才是。
> 改 20s 只是把僵尸取消从 60s 缩到 20s。

这句话是对的。把 60s 改成 20s 甚至 5s，**取消依然要等满整个超时窗口**——
用户点"取消"后界面纹丝不动，这是功能缺陷，不是体感问题。

正确做法：

```rust
tokio::select! {
    r = read_ack(...)        => r,   // 正常路径
    _ = cancel_rx.changed()  => Err(Canceled),  // 立即响应
}
```

超时值只决定**多久判定对端失联**，不决定**取消的响应速度**。两件事正交，都要做。

### 6.2 参数表

| 参数 | 现状 | 定案 | 理由 |
|---|---|---|---|
| chunk ACK 超时 | 60s | **自适应：`5s + chunk_size/1MB × 1s`**（16MB→21s，64MB→69s） | 固定 20s 会让慢设备误判：老安卓机写 eMMC、接收目录在 USB2.0 硬盘上时，16MB 可能超 20s。**误判失败 = 功能不可用，多等几秒只是体感** |
| 取消响应 | 等满 60s | **`select!` 立即生效**（§6.1） | 本阶段最重要的修复 |
| 单块重试次数 | 0 | **3** | 再多就是拿用户的带宽赌运气 |
| 重试退避 | 无 | **0 / 200ms / 500ms** | 局域网不需要长退避，长退避只会让传输显得卡死 |
| 连接建立重试 | 0 | **3 次，间隔 500ms** | 覆盖"对端 daemon 刚启动还没监听"这种场景 |
| 连续失败放弃阈值 | 无 | **连续 10 块** | 8 流并行时，网络级故障一秒就能攒满 10 块；单块偶发失败不会误触 |

## 10. 三件事的定案（2026-09-05）

**1. 续传拆不拆 → 拆**，但"留字段"要做实（见 §4.1）。
核心理由：「续错文件」和「不能续传」不是一个量级的失败。
mtime 匹配在 FAT32（2 秒精度）+ Android 10+ 写入限制下会出错，错了就是静默数据损坏；
sha256 虽然能兜住（报 mismatch），但用户看到的是"续传必失败"，
绕一圈回原点还搭上排查成本。

**2. 重试参数 → 自适应超时 + `select!` 取消**（见 §6）。
评审纠正了我原来的重心：超时值不是最大的问题，等待期间不 `select!` `cancel_rx` 才是——
改 20s 只是把僵尸取消从 60s 缩到 20s。同批参数（重试 3 次、退避 0/200ms/500ms、
连续 10 块放弃）照原案通过；连续 10 块的阈值考虑了 8 流并行时网络级故障的攒满速度。

**3. 连接复用 → 本阶段不做**（原定"做"，2026-09-05 复审后推翻）。

推翻的理由是我原先的收益判断站不住，逐项重算（并行流数默认 `min(CPU,8)` = 8 条，
**不是 2 条**——这一点我一开始也算错了）：

| 项 | 复用前 | 复用后 | 实际影响 |
|---|---|---|---|
| 建连次数（1GB / 16MB 块） | 64 | **8** | 8 倍，不是 32 倍 |
| 握手耗时 | 64 × 0.2ms ≈ 13ms | 8 × 0.2ms ≈ 1.6ms | 传 1GB 要几十秒，完全淹没 |
| TIME_WAIT | 64 个 | 8 个 | 占端口池 0.05%，**本来也不是问题**（我先前把它列为收益是夸大） |
| 失败机会 | 约 6.2%（按单次 0.1%） | 约 0.8% | 唯一实在的一项，但**重试能把两边都压到可忽略** |

结论：这是局域网工具，RTT 极低，复用省下的时间感知不到；
真正解决"传输中断要重来"的是**重试**，不是复用。

**更关键的是，先做复用反而会让重试变复杂**：复用后连接断了要判断"从哪个未确认块
继续"，而不复用时每块本来就独立建连接，重试就是"重新建连接再发一次这块"，
天然就这么工作。另外重发同一块是幂等的（`chunk_id` 相同 → 按偏移覆盖写），
连去重逻辑都不需要。

**什么时候把复用捡回来**（三选一即可，目前都不成立）：
1. `chunk_size` 调小——1GB 按 1MB 切是 1024 块，建连中招率会到 60% 以上，届时复用 + 重试一起上
2. 离开纯局域网——VPN / 跨网段 / 广域网，RTT 从 0.2ms 涨到几十毫秒，1024 次握手就是几十秒
3. 真机回归时发现大量 `connect` 失败日志

### 10.4 后续：复用已实现（2026-09-07）

应要求"阶段 4 全部做完（含 4.1 / 4.2）"，复用在本阶段一并落地了。
上面 §10.3 的收益判断（8 倍而不是 32 倍、TIME_WAIT 本来不是问题）**依然成立**——
做它不是因为收益变大了，而是为了不留半截工程。

**实现时发现先前的顾虑有一条是错的**，记在这里以免将来再被它吓退：

> 原文："更关键的是，先做复用反而会让重试变复杂：复用后连接断了要判断
> '从哪个未确认块继续'"

实际写的时候才发现：**停等模型下这个问题不存在**。发送方收到 ACK 才发下一块，
所以任一时刻"已发出的块里，最多只有一个未确认"——就是当前这一块。
连接断了就从当前块重建连接重发，不需要任何进度协商。
`send_chunk_with_retry` 里 `*conn = None` 然后重建，就是全部逻辑。

改动落点：
- 发送端：worker 持有 `Option<SendConn>`（`BufReader<TcpStream>`），跨块复用；
  失败时置空重建；这条流发完主动 `shutdown()` 让对端读到干净 EOF
- 接收端：`serve_data_stream` 加读帧循环，原来"一连接一块"没有循环
- `read_full` 替代 `read_exact`：后者在 EOF 只给 `UnexpectedEof`，
  分不清"正常发完"和"读到一半断了"；复用后 EOF 是唯一的结束信号
- `BufReader` 必须是**连接级**的：每块新建一个的话，它可能把下一个 ACK
  预读进自己的缓冲区然后随 drop 一起丢掉

**新旧版本混用的兼容性**（真实存在，记下来）：
- 旧发送端（每块一连接）+ 新接收端：兼容。新接收端读一帧后继续读，
  旧发送端发完就关连接 → 新接收端读到 EOF 正常退出，再 accept 下一条
- 新发送端（复用）+ 旧接收端：**会退化且很慢**。旧接收端读完一块就 return，
  不发第二帧的 ACK；新发送端等不到 ACK → 超时 → 重建连接。
  实际效果退化为"每块一连接 + 每块都要等满一个 ACK 超时窗口"，
  三次重试耗尽后整个传输失败。
  同版本发布时无影响，但真机回归要确认两端版本一致。

**4.3 的两个实现要点**（动手前先定，避免返工）：

1. **错误要分类**，不能一律重试。现在 `send_chunk` 失败统一返回
   `CoreError::Transfer(String)`，调用方分不出类型。但这两种情况该区别对待：
   - 连不上 / 写到一半断开 / 等 ACK 超时 → 网络瞬时故障，**重试**
   - 收到 `ChunkAck { ok: false }` → 对端明确说"这块没写好"，通常是磁盘满或没权限，
     **不重试**。按现在的超时算，白试三次就是 63 秒的无效等待

   做法：给错误加一个变体（或让 `send_chunk` 返回"可重试 / 致命"两种结果），
   重试循环只对前一种生效。

2. **重试是幂等的**，不需要去重。`chunk_id` 不变 → 接收端按
   `chunk_id × chunk_size` 算偏移覆盖写。即使上一块其实已落盘（只是 ACK 丢了），
   重发也只是原样再写一遍。

### 4.5 落地说明 + 顺带修掉的一个漏洞

**① `finalize` 的返回值从 `Result<()>` 改成 `Result<PathBuf>`**。
改名后实际落盘的是 `a (1).mp4`，而 `slot.final_path` 记的只是"首选名"。
调用方（UI 的"打开文件"）必须用返回值，否则点开的是一个不存在的文件。

**② 冲突检测放在 rename 那一刻，不是建槽时**。建槽到收完之间可能有别的传输
占用了名字，只有 rename 时的判断是真的。真被抢占（并发 finalize）时靠
`ErrorKind::AlreadyExists` 重挑一次名字——被抢的那个现在 exists 了，会自动跳过。

**③ 顺带发现并修掉：文件名没有做路径穿越防护**。
`create_slot` 直接用对端 offer 里的 `file_name` 做 `receive_dir.join(...)`。
`Path::join` 遇到绝对路径会**丢弃基目录**，加上 `..` 可以往上跳，
两者合起来意味着对端能指定接收目录之外的任意写入位置。
修法是 `safe_file_name()` 只取 `Path::file_name()`（`..`、空串、Windows 盘符
前缀都返回 None，兜底成 `unnamed`）。这是 4.5 之外的问题，但在改文件名逻辑的
路上撞见了，成本三行，就一起做了。

每步跑完整闸门（51 项测试 + 两端 analyze）后再提交。

### 4.3 落地时的两个补充决定

1. **`send_chunk` 的返回类型从 `Result` 换成 `ChunkResult`**
   （`Ok` / `Retryable` / `Fatal` / `Canceled`）。
   取消单独成一个变体而不是 `Fatal("canceled")`：否则调用方要靠比较错误字符串
   来区分"用户取消"和"真失败"，而两者终态不同（Canceled vs Failed），必然出 bug。

2. **重试耗尽即中止整条流，不"跳过失败的块继续传"**。
   原计划里有个 `MAX_CONSECUTIVE_CHUNK_FAILURES`（连续 N 块失败才放弃），
   实现时删掉了 —— 它隐含"跳过"，而跳过是错的：少一块，接收端
   `received_chunks` 永远凑不齐，`.part` 不会 finalize，发送方在 `/api/verify`
   处必然失败。晚失败不如早失败，还省了一整个文件的传输时间。

   顺带确认了重试的幂等性（设计文档里的第 2 点）在代码里成立：
   `storage.write_chunk` 是 `seek + 覆盖写`，`received_chunks[chunk_id]` 是布尔位，
   重发同一块不会让计数多算一次 —— 这点已由
   `retry_recovers_when_second_attempt_succeeds` 从行为上锁住。
