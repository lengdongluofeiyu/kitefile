### 几条定案的理由（值得留档）

**B1 为什么不编译「用户版 / 开发版」双版本**：真正的安全边界在 daemon 侧的
`--remote-admin`，UI 入口只是"方便找到功能"——藏它解决的是**用户困惑**，不是安全。
双版本会翻倍 dist 产物，且日常测的是开发版、用户版组合从未被测过。
将来真要分版，用 `flutter build --dart-define=FTCORE_DEV=1`（const 分支 + tree-shaking
真删代码），一行命令的事，现在不需要。
不砍的理由：砍了调试对端就只剩 adb。

**C1/C2 的判断标准只有一条**：会不会在不信任的 WiFi 上用。
家用 → 都不做也行；公司/公共 WiFi → 至少 5a。
5a 做、5b 缓的理由：5a 与接口分级同构递进（接口分类 → 设备分类），
配对弹窗复用 incoming 弹窗的交互模式，成本可控；
5b 是帧格式大改 + nonce 管理（P0-3 那种坑），家用威胁模型下收益配不上风险。

**C3 为什么 4 之后必须真机回归**：已经吃过"改了没验证、dist 里躺着旧包"的亏
（`?fileName` 那次）。回归覆盖：大文件双端互传、杀 App 重开后设备列表唯一性、
改名生效、取消响应速度。

**D2 为什么推迟是错的**：等到 build-all 才发现，那时上面已叠了阶段 4 传输核心改动，
排查范围翻倍，bisect 定位不到。纯 cargo 不碰 Gradle、CARGO_HOME 在 E 盘不占 C 盘、
增量两三分钟，当场跑的代价远小于事后排查。
（附带教训：查"依赖是否还被引用"不能只搜 `use bytes`，**crate 名内联路径**
如 `bytes::Bytes` 也要搜。）

## A. 阻塞阶段 4 的三个（最紧急，定了就能开工）

### A1. 阶段 4 的范围：跨重启续传（N3）要不要一起做？

**背景**：方案原计划 4.0（chunk_size 协商）和重试、续传一起做。我核对代码后建议拆开——
因为它们的工作量差一个量级，且续传会牵出 `source_mtime` 跨平台精度的坑（FAT32 只有 2 秒精度）。

**选项 A：拆 —— 本阶段只做 4.0 + 4.1~4.5（重试），续传挪到后续** ★
- 利：阶段 4 能快速落地；用约两成工作量解决九成实际故障（网络抖动、连接被掐）；
  避开 mtime 精度问题；重试所需的位图已经存在，改动面小
- 弊：进程重启后无法续传（传 1GB 传一半崩了要重来）；将来再加时可能要动协议

**选项 B：不拆 —— 按原方案一次做完**
- 利：一次做完整，不存在"将来返工"
- 弊：要新增元数据落盘（`file_id.meta`）、启动扫描、.part 过期清理三套机制，
  还会引入新的状态不一致风险；mtime 匹配一旦出错就是**续错文件**，
  比"不能续传"更糟——数据静默损坏且难以发现

**补充**：即使选 A，我也建议**现在就把协议字段留好**（`chunk_size` 已在 offer 里，
槽位元数据的结构现在定下来），这样将来加续传不用改线格式。这是"拆但不留坑"。

---

### A2. 重试参数，尤其是 ACK 超时从 60s 降到多少？

**背景**：现在 `send_chunk` 等 ACK 是 60 秒，期间不检查取消——用户点取消要等一分钟才有反应。

**选项 A：固定 20s** ★（原建议）
- 利：取消响应快；故障暴露快；局域网内 16MB 块落盘通常远低于 20s
- 弊：**慢设备会误判**。老安卓机写 eMMC、或接收目录在 USB2.0 移动硬盘上时，
  16MB 可能写超过 20s，导致本可以成功的传输被判失败

**选项 B：固定 30s**
- 利：给慢设备留余量，误判概率低
- 弊：取消响应慢一倍；仍然可能对极慢设备不够

**选项 C：按块大小自适应**（`超时 = 5s + chunk_size/1MB × 1s`，16MB → 21s，64MB → 69s）
- 利：大块给足时间、小块快速失败，两边都照顾到；逻辑只有一行
- 弊：多一个需要解释的参数；极端情况仍可能不够

**我的修正建议**：A 和 C 之间我倾向 **C**，因为项目目标设备含移动端，
而"误判失败"比"多等几秒"代价更高（前者是功能不可用，后者只是体感）。

**同批需要定的参数**：单块重试次数（建议 3）、退避间隔（建议 0/200ms/500ms）、
连续失败多少块后整体放弃（建议 10）。

---

### A3. 连接复用（4.1/4.2）做不做？

**背景**：现在每个 chunk 新建一条 TCP 连接。1GB 文件按 16MB 切片 = 64 次握手，
每次都可能失败。接收端 `serve_data_stream` 目前读一帧就返回，所以连接无法复用。

**选项 A：做** ★
- 利：**这是本阶段性价比最高的一项**。64 次建连变成 2~8 次（按并行流数），
  失败机会直接降一个数量级；同时省掉 64 次握手，性能也上去了——
  是"可靠性"和"性能"的公约数
- 弊：接收端要改成 while 循环持续读帧；需要处理"连接断了怎么接着传"（正好和重试配合）

**选项 B：不做，只加重试**
- 利：改动更小
- 弊：等于一边修漏水一边往船上凿新洞——失败源不减少，光靠重试兜底，
  重试逻辑会变得更复杂且效果打折

## B. 影响使用体验的两个（建议近期定）

### B1. mobile 的「遥控模式」怎么办？

**背景**：移动端 UI 里可以把 `_daemonHost` 填成对端 IP，去控制另一台设备上的 daemon。
阶段 2 加访问分级之后，这类请求默认会被 403——除非对方用 `--remote-admin` 启动。
现在界面没有任何提示，用户会看到"莫名失败"。

**选项 A：保留遥控 + 加明确的 403 提示** ★
- 利：功能不丢；用户看到提示就知道该怎么做（让对方加 `--remote-admin`）；改动只在 UI 层
- 弊：需要改 Dart 代码并处理错误分支；遥控依然依赖对方开了开关

**选项 B：去掉遥控入口，每台设备只管自己**
- 利：彻底简化；也更符合项目"对等节点（P2P）"的定位——每台设备自己跑 daemon，
  本来就不该由手机去遥控电脑
- 弊：失去远程管理能力；如果某个场景依赖它，砍掉会很痛

**选项 C：保持现状**
- 利：不用改
- 弊：留一个"看起来坏了"的坑，用户遇到只会觉得程序有 bug

### B2. C 盘只剩 1.2G，要不要清理？

**背景**：上一轮会话就是被 `ENOSPC`（磁盘写满）打断的。C 盘 200G 用了 199G。
已确认：`AppData\Local\Temp` 占 532M；cargo / pub / TEMP 缓存都已重定到 E 盘，
所以**目前不影响编译**。深层占用扫描跑了 40 分钟仍未出结果（C 盘文件太多，`du` 极慢）。

**选项 A：我先只清 `AppData\Local\Temp`（约 532M），其他不动** ★
- 利：立刻释放 1/4 的剩余空间；这是明确的临时目录，风险最低
- 弊：治标，C 盘依然紧张

**选项 B：等深层扫描出结果，找到真正的占用大户再一起处理**
- 利：能解决根本问题
- 弊：扫描可能还要很久；期间随时可能再触发 ENOSPC

**选项 C：你自己手动处理，我不碰**
- 利：你最清楚 C 盘上什么能删
- 弊：需要你自己花时间

**注意**：无论选哪个，我都会遵守"只删明确缓存、不动个人文件、删前列清单"的原则。

## C. 方向性的三个（决定项目往哪走）

### C1/C2. 阶段 5a（配对 token）和 5b（数据通道加密）做不做？

**背景**：这两个是方案里的"安全线"。5a 是设备间互相点"信任"、交换 token，
之后跨机接口都要带 `Authorization: Bearer`；5b 是把数据通道用 AES-256-GCM 加密。
**这两个要不要做，取决于你的目标使用场景**——这是最关键的一个判断。

**选项 A：两个都做**（方案原计划）
- 利：完整的安全模型。没有 token 时，局域网内任何人都能给你的设备发文件、
  探测你的设备；没有加密时，抓包就能还原传输的文件内容
- 弊：工作量最大的一块（配对流程 + 密钥派生 + 帧格式改造 + 两端 UI 弹窗）；
  配对会给首次使用增加摩擦（两台设备要互相点"信任"）

**选项 B：只做 5a（配对 token），不做 5b（加密）**
- 利：挡住"顺手攻击者"（未授权设备不能调用你的接口），成本低很多
- 弊：数据仍是明文，能被抓包还原。方案里也明确写了：
  token 是明文头，被动嗅探可重放，**防顺手攻击者、不防盯着你的攻击者**

**选项 C：两个都先不做，先完善功能与体验**
- 利：把精力放在传输可靠性、两端 UI 体验上，产品更快可用
- 弊：只适合完全可信的网络（自家、小团队）。拿到公司或公共 WiFi 上，
  等于把文件目录向整个网段敞开

**我的看法**：如果这是**自己家 / 小团队内部**用的工具，C（或 B）是务实的；
如果可能出现在**公司网络、公共 WiFi** 这种不可信环境，A 是必要的。
我没有你的使用场景信息，这个得你判断。

### C3. 阶段 5 的推进顺序

**背景**：方案给的关键路径是 `4 → 5a → 5b`，理由是安全优先；
5c（Dart 共享包）要等 4 定稿后做（否则协议没定就抽 UI 会白抽）；
5d（手动添加 IP）依赖 5a；5e（进度粒度）最独立。

**选项 A：按方案顺序 4 → 5a → 5b → 5c/5d/5e** ★
- 利：安全线优先，且符合依赖关系
- 弊：安全功能用户"看不见"，连续做两个大阶段却没什么可感知的改进

**选项 B：4 → 5e/5c（体验与代码结构）→ 5a → 5b**
- 利：先做出用户能感知的改进（进度更细、两端代码复用），团队士气更好
- 弊：安全线延后，这段时间里产品仍暴露在局域网风险中

**选项 C：4 → 先做一次完整回归与真机验证 → 再决定**
- 利：先把 1~4 的成果跑通端到端（含真机传输），确认地基稳了再往上盖
- 弊：进度看起来慢

## D. 技术债两个（可缓，但最好别一直拖）

### D1. `build-all.ps1` 的双 BOM 已第二次复发

**背景**：阶段 1 修过一次，跨会话期间又被改回去了。双 BOM 会让某些工具把文件首行解析错。

**选项 A：加一个 BOM 自检闸门**（在 build 脚本开头检查，重复 BOM 就报错）
- 利：立刻能挡住复发，成本极低
- 弊：治标——没定位到是哪个工具在写回时追加的 BOM

**选项 B：先花时间定位根因**（查是哪个环节在写这个文件）
- 利：治本
- 弊：可能要翻不少历史操作，收益不高

**选项 C：不管它**
- 利：省事
- 弊：会一直复发，每次都要手动修

**我的建议**：先 A（加闸门，5 分钟），等哪次又触发时再顺藤摸瓜查根因。
