## 0. 一句话概要

**把信任模型从「全网默认互信」改成「先配对、后信任」**：配对模式控制可见性与可配对性，
配对产出证书指纹 + 双向 per-peer token，控制面与数据面全部走 TLS；
已配对设备保持现有自动发现体验，未配对设备默认拒绝。

先拍板三件事（其余见 §15）：

| # | 问题 | 我的倾向 |

| Q2 | 端口重划：7878 收回本机、新开 7880 跑局域网 TLS | **是**（UI 端口常量零改动） |
| Q3 | 新旧版本互传：做不做明文降级兼容 | **不做**（旧版可见地失败） |

> 已拍板：Q1=TLS、Q2=端口重划、Q3=不做降级（随方案批准）；
> 鉴权=mTLS 客户端证书（评审选定）。§15 其余细节无异议按倾向执行。

## 2. 威胁模型（诚实边界）

### 防

| 攻击 | 对策 |
|---|---|
| 局域网任意设备调用你的接口（发文件刷弹窗、读接收目录、探测设备表） | Remote 接口 fail-closed：无 token / 无配对会话 → 403 |
| 伪造设备名诱导「信任」 | 确认码 + TLS 客户端证书：冒充他人指纹过不了握手签名，中间人使两边确认码不一致 |
| 被动嗅探还原传输的文件内容 | 控制面 + 数据面全 TLS（ECDHE 前向保密） |
| 重放 / 抢注凭据（原 5a 的 Q3 竞态） | 配对会话化：配对结果只在一次性 session 内落库，不存在按 device_id 直推 |
| 未配对设备无限制发 offer 刷弹窗（原 N12） | 未配对根本到不了 offer；`pair/hello` 同 IP 限频 10s/1 次 |

### 不防（写进文档，别过度承诺）

| 场景 | 说明 |
|---|---|
| **已配对设备本身被攻陷** | 它持有有效 token 与对端 pin，等同你本人。缓解只有「删除设备」撤销 |
| 被动嗅探者知道「谁在网里、谁和谁在通信、传了多大」 | mDNS 与流量元数据本就明文可见；本设计不隐藏存在性 |
| 用户不比对确认码的 TOFU | 确认码必须两屏人工比对，跳过比对 = 只剩 TLS 加密无身份保证 |
| 配对模式下同名社工（冒充「你的笔记本」发起配对） | 残留风险：靠 IP/平台展示 + 提示「确认对方设备在场」；已配对的 device_id 被冒用直接 409 |

## 3. 总体设计

```text
┌────────────────────────────────────────────────────────────────┐
│ ① 发现平面（明文，基本不变）                                     │
│    mDNS：id / name / ports + 新增 pair=0|1                      │
│    探活：60s TCP 握手 ×3（TCP 层，与 TLS 正交）                   │
├────────────────────────────────────────────────────────────────┤
│ ② 信任平面（新增）                                               │
│    配对模式（120s TTL，主动开启）                                 │
│      → 配对握手（TLS 双方出示客户端证书 + 联合确认码 + 会话化落库）  │
│      → peers.json（对方证书指纹 pin）                             │
│    鉴权：Remote 档必须「客户端证书 ∈ 已配对表」或合法配对会话       │
├────────────────────────────────────────────────────────────────┤
│ ③ 传输平面（改造）                                               │
│    7878  127.0.0.1 明文  ← 本机 UI / WS（现状不变）                │
│    7880  0.0.0.0   TLS   ← 局域网控制面（新，mDNS 广播此端口）       │

└────────────────────────────────────────────────────────────────┘
```

生命周期（总图）：

```text
[未配对·正常] ──双方开启──▶ [配对模式] ──确认码一致·双方点确认──▶ [已配对]
     ▲                         │ 120s 超时自动退出                    │
     └─────取消配对（删记录）────┘◀──── 上线自动发现·按需 TLS 连接 ◀────┘
```

## 4. 身份与密钥模型

### 4.1 每台设备一把长期身份密钥（首启生成，此后不变）

- 算法：**Ed25519**（签名 + TLS 1.3 服务端认证同一把钥匙；握手密钥交换由 TLS 的
  临时 ECDHE 提供前向保密，**不需要**单独的静态 X25519）。
- 载体：自签 X.509 证书（rcgen 生成），`CN = device_id`，与 `.kitefile-identity`
  同目录：`identity_cert.pem` / `identity_key.pem`（私钥文件权限 0600）。
- 指纹：`fp = SHA-256(证书 DER 字节)`，十六进制——配对 pin、确认码、UI 展示都用它。
  （对自签单证书场景，整证书哈希与 SPKI 哈希等价：我们 pin 的就是握手时收到的
  那张证书本身，且证书永不重签。实现上免去 X.509 解析依赖。）
- **不扩展现有 `.kitefile-identity` 文件格式**（它是 {id, name} 的简单 JSON，
  动它会牵连加载逻辑；新文件并列存放）。

### 4.2 配对产出什么（mTLS 定案）

| 产物 | 内容 | 用途 |
|---|---|---|
| 对方证书 | 证书 DER + `fp`（按 `device_id` 索引） | 之后每次 TLS 握手：服务端收客户端证书查表放行，客户端校验服务端证书 pin |
| 配对会话 | 一次性 `pairing_session`（60s） | 绑定同一连接上的 hello→确认→落库全过程，防冷启动直推 |

### 4.3 为什么用客户端证书，而不再要 token（评审定案）

| | mTLS 客户端证书（选定） | token + PoP（初稿） |
|---|---|---|
| 身份从哪来 | TLS 握手本身：rustls 校验 CertificateVerify → **出示证书即证明持有私钥**，PoP 免费 | hello 里声称指纹 + 应用层签名（要引 X.509 解析依赖） |
| 请求鉴权 | 连接级：证书 ∈ peers 表即通过 | 请求级：每条 HTTP 带 Bearer，数据通道加 AUTH 行 |
| 撤销 | 删一条记录 | 删一条记录（等价） |
| 出错面 | 少三套机制（token 存储、常数时间比较、AUTH 方向） | 沿用 5a 旧案，机制多 |

代价：Web 实验端（浏览器）配客户端证书麻烦——`web/` 本就是实验位，不做承诺。

### 4.4 密钥生命周期

- 重装 / 删数据目录 → 身份密钥没了 → 对方 pin 校验失败 → **需要重新配对**（预期行为）。
- 「取消配对」= 删本地记录（pin + token 双向作废）；对方需同样删除或接受 403 后重配。
- 不做密钥轮换、不做证书有效期轮换（LAN 场景收益不抵复杂度）；
  有效期用 rcgen 默认的宽松区间，**信任基于指纹 pin，不校验有效期**。

## 5. 配对模式（可见性开关）

### 5.1 状态与作用

| 状态 | mDNS `pair` TXT | 未配对设备在对方 UI | `POST /api/pair/hello` |
|---|---|---|---|
| 正常（默认） | `pair=0` | **不显示** | 403 |
| 配对模式（手动开启，120s TTL） | `pair=1` | 显示为「可配对」 | 受限放行（限频 + 单 pending） |

三重作用：**① 可见性标志**（UI 过滤）　**② 配对接口的门**　**③ 弹窗骚扰的门**（未配对
设备连 offer 都发不进来，N12 由结构解决而非限频兜底）。

### 5.2 实现（已核对 mdns-sd 0.11.5）

- 进入 / 退出配对模式 = 重新调用 `register()` 携带新 TXT
  （`service_daemon.rs:286` 文档原文：*"To re-announce a service with an updated
  service_info, just call this register function again."*）。
- 监听端收到变化的 TXT 会当作新记录入库（`dns_cache.rs:183-186` 返回 `true`），
  进而**再次触发 `ServiceResolved`**（`service_daemon.rs:1780-1794`）——
  现有 `discovery.rs` 的事件循环已能消费，只需在 upsert 时读出 `pair` 字段。
- 旧版客户端会忽略未知 TXT 键，**不解析即无感**，向后兼容。
- 已知细节：cache-flush 下新旧 TXT 并存窗口 ≤1s（`dns_cache.rs:143-169`），
  取插入序首条（新的）；配对状态晚 1~2 秒到达可接受。

### 5.3 可见性的诚实声明

mDNS 是组播，**本设计不隐藏「这台设备在网里」**——隐藏的是「这台设备可被配对」的
UI 状态与配对接口的可达性。被动嗅探者照样能看到广播包；真正的安全边界在
TLS + token，不在隐身（§2 已列）。

### 5.4 UI 过滤规则（定死）

```text
设备列表展示 ⇔  已配对   ∨  （未配对 ∧ pair==1）
```

未配对且 `pair==0` 的条目：daemon 设备表可保留（诊断用），**UI 一律不显示**。
配对成功或退出配对模式后，对端 UI 上该未配对条目随之消失。

## 6. 配对流程

### 6.1 时序

```text
A（发起方，已进入配对模式）                B（接收方，已进入配对模式）
  │
  │ A 从设备列表看到 B（pair=1）→ 点「配对」
  │
  │════ TLS 连接 A→B:7880 ══════════▶│  握手即交换证书：
  │   A 出示客户端证书 certA            │  B 收到 certA（rustls 校验
  │   A 校验服务端证书 → fpB            │  CertificateVerify = A 持有私钥，
  │                                   │  应用层 PoP 不再需要）
  │──── POST /api/pair/hello ───────▶│  {device_id, name, platform}
  │     （本机算 C = 确认码(fpA,fpB)）  │  B: 已配对 409；busy 409；限频 10s/IP
  │◀─── {pairing_session} ────────────│  本机也算 C = 确认码(收到的certA, 自己)
  │                                   │
  │  UI：「等待 B 确认 · 确认码 C」      │  弹窗：「A(192.168.1.5/Windows)
  │                                   │        请求配对 · 确认码 C」
  │            ──── 用户在两屏比对 C，一致则在 B 点「确认」 ────
  │                                   │
  │◀══ POST /api/pair/confirm ═══════│  {pairing_session}（B 侧已确认）
  │    A: 有 pending session →         │
  │      写入 peers[B] → 200           │
  │──── 200 ─────────────────────────▶│  B: 收到 200 → 写入 peers[A]
  │                                   │
  │  双方完成，配对模式倒计时若无其他操作则退出
```

两阶段写的理由（崩溃窗口自愈）：A 先写、B 收到 200 后才写——
若 200 丢失，只有 A 单边已配对，B 仍是未配对 → A 重新发起 hello 不会被
409 挡住，重走一遍即可修复；反过来 B 先写则会把「B 已配对、A 没有」
锁死成 409。取消 = 用户不点确认，会话 60s 超时作废（B 未写任何东西）。

### 6.2 确认码算法（双方独立算出同一串）

```text
fp_lo = min(fpA, fpB)，fp_hi = max(fpA, fpB)          // 字典序，与谁发起无关
raw   = SHA-256("kitefile-pair-v1" || fp_lo || fp_hi)
C     = 前 4 字节大端 u32 % 1_000_000，左补零到 6 位   // 如 "048392"
```

- 两边输入相同（各自的 fp + 对方的 fp）→ 输出相同；与计算顺序无关。
- 约 20 bit 熵，对「人工比对 + 主动中间人每次都要猜中」足够；
  比对失败用户会看见不一致并重来，这是主要防线。

### 6.3 为什么中间人打不进来（推演，写给评审）

设中间人 M 夹在 A、B 之间：

1. **A 侧**：A 的 TLS 对端是 M，算出 `C_A = f(fpA, fpM)`；B 算 `C_B = f(fpM被见的客户端证书, fpB)`。
2. 要 `C_A == C_B` 需 `{fpA, fpM} == {客户端证书, fpB}`：
   - M 想向 B 出示 A 的证书 → 没有 A 的私钥就产生不了
     `CertificateVerify`，**TLS 握手直接失败**（rustls 在握手层校验，应用层拿不到插手的机会）；
   - M 只能出示自己的证书 → B 侧确认码含 fpM、A 侧确认码含 fpB，必然不一致；
   - M 在 B 面前冒用「A 的指纹」而不持有私钥 → 同第一条，握不过去。
3. 结论：**确认码 + mTLS 客户端证书 + 会话化** 三者缺一才会漏。
   等价于蓝牙 SSP 的数字比对。

### 6.4 边界行为（定死）

| 情况 | 行为 |
|---|---|
| 对方不在配对模式收到 hello | 403「对方未开启配对模式」（限频后可改静默） |
| device_id 已在 peers 中 | 409「已配对，请先在设备管理中解除」（Q3：拒绝覆盖） |
| 同时收到第二个 hello | 409 busy（单 pending，简化状态机） |
| session 超时（60s 未完成） | 作废，双方清 pending |
| confirm / hello 携带无效 session | **403 直接拒绝**——原 5a 的 Q4「冷启动推送弹窗」问题被会话化自动闭合，不存在该分支 |
| 确认码不一致 | 用户不确认 → 60s 超时作废；UI 提示「确认码不一致，疑似有人拦截，请核对设备」 |
| 发起方中途退出配对模式 | 会话作废 |
| 同 IP 10s 内重复 hello | 静默丢弃 + `warn!`（原 N12 的限频挪到这里） |

## 7. 已配对设备列表与「自动发现、连接」

### 7.1 peers.json（daemon 数据目录）

```json
{
  "version": 1,
  "peers": {
    "<device_id>": {
      "name_hint": "办公本-Win",
      "platform": "windows",
      "cert_der": "<base64 证书 DER>",
      "fp_sha256": "ab12…",
      "paired_at": 1768000000
    }
  }
}
```

- 索引键 **`device_id`**（Q5 原样：换 IP 不掉信任；IP 变化由 mDNS 重新解析）。
- 鉴权时按连接收到的客户端证书整表比对 `fp_sha256`（常数条目线性扫即可，
  LAN 设备数个位数）。
- 撤销 = 删该条目 → 该证书的双向 TLS 身份立即失效。
- 拒绝任何自动覆盖；重配对必须走 UI 显式「重新配对」。

### 7.2 「自动发现、连接」到底改了什么

**现状已经是自动发现**（mDNS 全量广播 + 探活）。本设计的增量是**信任分层**：

| | 配对前（现状语义） | 配对后 |
|---|---|---|
| 发现 | 看见全网设备 | 已配对：永远看见（在线/离线）；未配对：仅 `pair=1` 时看见 |
| 发起传输 | 点了就能发（对方弹窗） | 已配对：点了就能发（对方照旧弹窗）；未配对：**无入口** |
| 接收 offer | 全网谁都能发 | **仅已配对**（token 校验通过） |
| 连接成本 | 每次 TCP+HTTP | TCP + TLS 握手（LAN 上 +1 RTT，可忽略；连接复用已由阶段 4 落地） |

明确的非目标：**「自动连接」≠「自动接受」**——已配对设备上线即可见、可一键发送，
但**接收弹窗保留**（被攻陷的配对设备不能变成静默推送渠道，见 §2）。

### 7.3 上线 / 离线

- 复用现有机制：mDNS `ServiceFound/Resolved` + 60s TCP 探活，**零新增协议**。
- 不做常驻长连接、不做 TLS 会话恢复（按需连接已够快；列为将来可选项，非 v1）。

## 8. 传输平面改造（端口 + TLS）

### 8.1 端口重划

| 端口 | 绑定 | 协议 | 服务对象 | 变化 |
|---|---|---|---|---|
| 7878 | `127.0.0.1` | 明文 HTTP | 本机 UI / WS / FFI（现状路径） | **绑定范围从 0.0.0.0 收回 127.0.0.1** |
| 7880 | `0.0.0.0` | **HTTPS（TLS1.3）** | 局域网控制面：offer / resp / verify / cancel / pair / whoami | **新增**；mDNS TXT `gateway_port` 广播 7880 |
| 7879 | `0.0.0.0` | **TLS**，握手后先 `AUTH` 行 | 数据通道 | 换传输层，帧格式不动 |

选择依据（Q2）：

- **UI 两个 Dart 端的端口常量零改动**（仍连 `127.0.0.1:7878` 明文）——
  回环流量本来就不经过网卡到外部，明文无威胁，还省掉 Dart 证书校验的全部麻烦。
- 探活循环探的是 mDNS 里的 `gateway_port` → 自动变成 7880 的 TCP 握手，**代码不用改**。
- 明文服务端只听回环 → 远程摸到明文口在结构上不可能，比中间件里判 `is_loopback`
  更硬（后者仍保留作纵深防御）。

### 8.2 TLS 具体做法

- crate：**rustls（ring 后端）+ rcgen**。不用 openssl 系（Android 交叉编译纯 Rust 友好）。
  ⚠️ rcgen / rustls 的加密后端在 `aarch64-linux-android` 下是否顺编，**第一阶段当场跑**
  （呼应 decisions D2 的教训：别等 build-all 才发现）。
- 服务端：每设备一张自签证书；rustls 单 `ServerConfig`。
- 客户端校验：按「预期对端 device_id」取 peers 中的 `fp` 与对端证书 SPKI 比对，
  不匹配即断（**无 pin 的连接只允许出现在配对流程中**，配对流程靠确认码兜身份）。
- 每条 TCP 连接一次 TLS 握手（LAN 上 +1 RTT）；阶段 4 已做连接复用，
  **不是**每 chunk 一次握手。

### 8.3 数据通道

```text
TCP connect → TLS 握手
             服务端：收客户端证书（P3 起查 peers 表放行）
             客户端：校验服务端证书 == 配对时的指纹 pin
           → [24B header][data] 帧原样流式读写   ← 帧格式零改动
```

- **废止 5b 原案的全部帧改造**：N7（+28 字节布局）、N8（capacity 预留）、
  N13（key_check nonce）、N6（AUTH 行方向）随 token/AES-GCM 方案一并废止
  （见 §14）——数据通道的对端认证由 TLS 客户端证书完成，不再需要应用层 AUTH。
- TLS 记录层自己的 tag/nonce 由 rustls 管理，不进业务帧。

### 8.4 降级与兼容（Q3）

- **不做明文降级**：旧客户端拿明文 HTTP 打 7880 → TLS 握手失败，可见地报错；
  旧客户端读 `gateway_port=7880` 后仍按明文打 → 同样失败。
- 不提供 `--no-tls` 逃生阀（有阀就会被默认打开）。
- 结论：**新旧版本互传不支持**，release note 显式写明两端需同版本。
  代价 = 老用户升级摩擦；收益 = 不存在协议降级攻击面。

### 8.5 受波及的远程调用方（逐一核对）

| 调用方 | 现状 | 改法 |
|---|---|---|
| daemon → daemon（offer/resp/verify/cancel/peer-resume） | 明文 7878 | HTTPS 7880；客户端出示证书；TLS 校验对端 pin |
| CLI `kitefile-cli` 远程 whoami/list | 明文打候选端口 | 走 7880 HTTPS（封装共享的 rustls 客户端）；whoami 免配对（见 §9） |
| 遥控模式（移动端填对端 IP，B1 已定为开发者功能） | 明文 7878 | 改打 7880 + 证书 pin；实现前维持 B1 的 403 文案 |
| `/ws/progress` 远程（遥控场景） | — | **v1 不做**（本机回环不变；遥控的远程 WS 等做遥控时再说） |
| 探活循环 | TCP 层 | 不受影响 |
| web/ 实验前端 | 直连 | 标注为实验，随本次一并切 7880 或显式声明不可用 |

### 8.6 性能注意

- TLS 流式加密在 x86/ARM NEON 下量级为 GB/s，局域网（≤1Gbps）通常不是瓶颈；
  **验收跑一次 1GB 明文 vs TLS 对比**（P4 验收项），损耗 >30% 再议。
- 内存：rustls 每连接有记录缓冲，与现有 8 流并行叠加——验收时看峰值，
  不新增 16MB 级的大块拷贝（这是当年选 AES-GCM in-place 的顾虑，rustls 自带缓冲管理）。

## 9. 接口与分级表变更

### 9.1 新增路由（全部登记进 classify 表，防 `test_classify_covers_all_routes` 红）

| 方法 | 路径 | 档位 | 鉴权 |
|---|---|---|---|
| POST | `/api/pair/mode` | LocalOnly | 本机 UI：进入/退出配对模式 `{enabled}` |
| GET | `/api/pair/mode` | LocalOnly | 本机 UI：查状态（剩余秒数） |
| POST | `/api/pair/start` | LocalOnly | 本机 UI 发起：daemon 代跑远端 hello，返回 `{pairing_session, code}` |
| POST | `/api/pair/decide` | LocalOnly | 本机用户确认/拒绝 `{session, accept}`，daemon 执行远端 confirm |
| GET | `/api/peers` | LocalOnly | 已配对设备列表 |
| DELETE | `/api/peers/:device_id` | LocalOnly | 解除配对 / 撤销 |
| POST | `/api/pair/hello` | Remote | **配对模式门**：接收方必须 `pairing` 中；限频；单 pending；凭据 = TLS 客户端证书（尚未入表，握手已验私钥） |
| POST | `/api/pair/confirm` | Remote | 携带有效 `pairing_session`（会话化，见 §6）；A 侧落库后回 200，B 收 200 才落库 |

### 9.2 既有 Remote 档鉴权变更（mTLS 定案）

| 接口 | 鉴权（在分级之上新加的一层） |
|---|---|
| POST `/api/incoming`、`/api/incoming-resp`、`/api/verify/:id`、`/api/cancel/:id`、`/api/peer-resume/:id`、`/api/peer-resumed/:id` | 连接的**客户端证书 fp ∈ peers 表**；否则 401。fp 由 TLS accept 循环注入请求扩展（`PeerFingerprint`），handler 层可见 |
| GET `/api/whoami` | **免配对**（诚实说明：它泄漏的 name/ports 与 mDNS TXT 广播的内容完全重合；5d 手动添加与版本诊断依赖它） |
| POST `/api/pair/hello`、`/api/pair/confirm` | 配对会话（9.1），不要求已配对 |

- 本机回环口（7878）上的请求不进证书检查（`is_local` 路径，现状不变）。
- `allow_remote_admin`（Q1 原裁决）**仍然成立**：分级放宽 ≠ 免鉴权，两者正交；
  遥控走 7880 时同样要过证书 ∈ peers 检查。
- 未配对 → 一切传输类接口 401，响应文案给可操作提示（「请先与该设备配对」），
  不只甩状态码（沿用 403 带 `--remote-admin` 提示的思路）。
- 数据通道无应用层 AUTH：服务端在 TLS 握手收客户端证书，P3 起对未配对证书
  拒绝握手（rustls 侧查表）或握手后首帧拒收——实现取前者。

### 9.3 鉴权检查挂法

在现有 `access_guard`（分级）**之后**加一层 `auth_guard`（P3 实现），顺序固定：

```text
request → access_guard（分级，现状） → auth_guard（证书 ∈ peers，P3） → handler
```

- 分级保持 (Method, Path) 纯函数可单测；auth_guard 读 `PeerFingerprint` 扩展查表。
- `PeerFingerprint` 扩展由 **P1 的 TLS accept 循环**注入（P1 只注入、不拦截，
  「不改任何鉴权行为」的承诺靠这一条落实）。

## 12. 实施拆分（每步独立可验收）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1 · 身份 + TLS 基建** | 首启生成密钥/证书；双监听（7878 回环明文 / 7880 TLS）；mDNS `gateway_port` 改广播 7880；CLI 远程调用切 HTTPS；**不改任何鉴权行为**（TLS 侧只注入 `PeerFingerprint` 扩展、不拦截；客户端证书请求但接受任意） | 现有测试全绿（改绑端口与客户端）；**当场跑 `aarch64-linux-android` 交叉编译**（D2 教训）；两台真机新版本互传回归 |
| **P2 · 配对模式** | 状态机 + TTL + mDNS `pair` TXT（re-register）+ UI 开关 + 设备列表过滤 | 一端开配对模式，另一端 1~2s 内看到「可配对」；超时自动消失；旧版客户端无感 |

| **P4 · 数据通道 TLS** | 7879 包 TLS + AUTH 进 TLS；废止 5b 相关 TODO | 1GB E2E sha256 一致；明文 vs TLS 吞吐对比记录；8 流并行无 FD/内存异常 |
| **P5 · 收尾** | 设备管理 UI 完整（改名跟随、删除、重配对）、回归清单、release note（版本互不兼容声明） | 走一遍 regression-checklist 风格的真机回归：配对、传输、取消、重启、杀进程、换 IP（DHCP 续租） |

依赖：P3 ← P1+P2；P4 ← P1；P5 ← P3+P4。**P1 是关键路径**，其 TLS 后端一旦
在 Android 上编不过，Q1 要当场重议（备选：Noise/snow，纯 Rust 无 C 后端）。

## 13. 测试与验收

### 单测

1. `classify` 覆盖新路由（扩展既有 `test_classify_covers_all_routes`）。
2. **（P1）** tls 模块：身份生成与复用（同目录二次加载 fp 不变）；accept-any 客户端
   与服务端完成握手；`pinned` 校验——指纹对通过、错断。
3. **（P1）** 双端口：回环口明文可达、LAN 口必须 TLS 握手成功才进 handler；
   两个 listener 各自的 whoami 广告端口正确（回环 7878 / LAN 7880）。
4. **（P3）** 鉴权：无证书/未配对证书 → 401；已配对证书 → 放行；
   `PeerFingerprint` 扩展注入正确。
5. 配对会话（P3）：过期 / 伪造 session / 已配对 device_id 409 / busy 409。
6. 确认码：`(fpA,fpB)` 与 `(fpB,fpA)` 输出一致；算法版本盐变更即变码。
7. `peers.json`（P3）：原子写、损坏文件降级为「空表 + warn」而非 panic、拒绝覆盖。
8. 配对模式 TTL（P2）虚拟时间到期（tokio test-util，沿用 A3.1 手法）。
9. 未配对请求全部 Remote 传输接口 → 401（fail-closed 防回归，P3）。

### 集成 / 真机

1. 双 daemon 全流程：配对 → 传输 → 解除 → 401。
2. TLS 校验：替换对端证书（自签另一张）→ 客户端必须断连。
3. 中间人演练（脚本级）：代理转发改证书 → 确认码两侧不一致（断言算法层即可，
   真 MITM 模拟做成脚本属可选）。
4. 1GB E2E + 吞吐对比（§8.6）。
5. 杀进程重开：身份、peers、配对模式状态恢复正确；配对模式不跨重启复活（重启默认关）。
6. 换 IP（重启路由器）：mDNS 重新解析后配对信任保持（Q5 验收）。
