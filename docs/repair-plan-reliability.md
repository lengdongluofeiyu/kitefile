# KiteFile（filetransfer）修复方案 · 可靠性与结构收敛

> 文档用途：交给**新的实现 agent** 直接开工。自包含，不依赖会话历史。  
> 范围依据：批判性评审 + 与维护者讨论后的定稿。  
> **明确不做**：安全配对/加密（另议）、web 端（有真实需求再做）、断点续传（跨重启）、iOS/macOS。

---

## 0. 项目一页纸

| 项 | 说明 |
|----|------|
| 是什么 | 局域网文件传输：Rust 核心 daemon + 桌面/手机 Flutter UI |
| 路径 | 仓库内 `core/`、`desktop/`、`mobile/`、`web/`、`docs/`、`scripts/` |
| 架构 | 一个 Rust 引擎：mDNS 发现、HTTP/WS 网关（默认 7878）、TCP 数据通道（默认 7879）；桌面用子进程 daemon，手机 FFI 进程内 |
| 传输模型（现行） | 文件按字节切成 N 段连续区间，N 条 TCP 流各写一段；流内顺序写、**无分块 ACK**；流数按文件大小自适应（约 4MB/流，上限 `parallel_streams`）；整文件 sha256 传完后 `/api/verify` 补发 |
| 入口 | 桌面 `desktop/`，构建 `scripts/build-all.ps1`（Windows 下缺 `%PROGRAMFILES(X86)%` 时用 `scripts/build-all-fix.ps1`） |
| 测试闸门 | `cargo test`（core 全量）+ `flutter analyze`（desktop/mobile）；**每个独立修复过测后必须 git commit** |

### 现行协议（实现时以代码为准，此处摘要）

- 控制面：HTTP offer/accept/reject/cancel/verify + WS 进度/incoming。
- 数据面：`StreamHeader`（file_id 前缀、stream_id、start_offset、data_len）+ 原始字节。
- `stream_layout(file_size, stream_count)` 切段；offer 携带 `stream_count`。
- 停等 ACK 模型已废弃（见 `341f63c`），文档里若再出现「chunk ACK」一律以代码为准。

## 2. 现状摘要（为何要做）

| 问题 | 现状（已与代码核对） |
|------|----------------------|
| 无 idle 超时 | `http_post_json`、数据流 `read/write` 可无限等待；仅有决策 60s、等 Accept 70s、探活约 2s |
| 单流失败 | 各流独立跑完，join 时才合并错误；**一条断了兄弟流继续烧带宽**，sha256 整文件作废 |
| UI 在线徽标 | 运行期 devices 轮询失败被 `catch (_) {}` 吞掉；WS 断开不改徽标 |
| FFI 生命周期 | `INIT_LOCK` 为 `OnceLock`，shutdown 后无法二次 init |
| 手机存活 | 无前台保活；锁屏/被杀 = 进程内 daemon 消失，进度在内存 Map |
| 类型分叉 | 进度等模型 core/desktop/mobile 各写一份；desktop `as num` 硬转，mobile `as num?) ?? 0` |
| UI 巨石 | 双端各 1000+ 行 State，业务约七成复制后漂移；批决策状态机两套 |
| 发布卫生 | Android `com.example`、debug 签名、权限偏大、so 仅 arm64；CI 不构建桌面/APK |
| 其它 | sha256 保险丝 120s 裸 sleep；`http_post_json` 双份；`PROTOCOL_VERSION` 零引用；注释残留旧模型 |

## 3. 工作流 A · 可靠性与故障面（P0）— **已定稿**

### 3.1 超时模型

三层语义，**默认值只定义一处**，各处复用：

| 层 | 含义 | 覆盖 |
|----|------|------|
| 连接建立 | TCP connect 上限 | 数据流连接、HTTP 客户端 |
| 空闲超时 | 读/写连续无进展 | 数据流收发、HTTP 响应读 |
| 任务总超时 | 可选，防止极端慢速占坑 | 单次传输任务 |

超时错误在传输中段按 **可重试** 处理（见 3.4）；决策 60s 超时**不是**传输故障，不进入重试。

### 3.2 单流失败 → 中断可续（维护者定稿）

**原则**：「取消/作废」≠「中断可续」。一条流失败时：

1. **提示失败**（进入 `Interrupted`，见状态机）。
2. **其余流暂停**：停止继续发送/落盘新数据，**保留已写入段与槽位**，不 abort、不删 .part。
3. 用户可选择 **继续传输（重试）** 或 **取消**。
4. 重试 **只调度未完成的流/段**；已完成段不重复传。

#### 状态机

```text
InProgress ──流失败(可重试,自动重试耗尽)──► Interrupted
InProgress ──流失败(不可重试)────────────► Failed
InProgress ──全段完成+sha256─────────────► Completed
InProgress ──用户取消────────────────────► Canceled
Interrupted ──用户「继续传输」───────────► InProgress（只传未完成段）
Interrupted ──用户「取消」───────────────► Canceled
Interrupted ──resume 时槽位丢失等────────► Failed
```

| 状态 | 槽位/.part | 其它流 | UI 角标 |
|------|------------|--------|---------|
| `InProgress` | 保留 | 进行中 | 传输中 / 重试中 |
| **`Interrupted`**（新增） | **保留** | **暂停** | 已中断 |
| `Failed` | 按现策略 | — | 传输失败 |
| `Canceled` | 按现策略 | — | 已取消 |
| `Completed` | 已 finalize | — | 已完成 |

#### 恢复粒度

- **恢复单位 = 流/段**（`stream_count` + `stream_layout` 在 offer 时锁定，**重试期间不得重算**）。
- 重试：只处理 `streams_done[i] == false` 的段。
- **整段从 `start_offset` 覆盖写**（幂等），第一期不做段内字节级续传。

### 3.3 自动重试（维护者：需要）

| 项 | 设定 |
|----|------|
| 触发 | 段失败且错误**可重试** |
| 次数 | 每段自动 **2 次**（共 3 次尝试） |
| 退避 | 0.5s、1.5s |
| 期间状态 | 仍为 `InProgress`，UI 显示「重试中」 |
| 耗尽 | → `Interrupted`，通知用户 |

### 3.4 可重试 / 不可重试（维护者已确认）

**主原则**：换个连接、原样重写同一段，有没有可能变好？可能 → 可重试；再试也改变不了结果 → 不可重试。

子标准（须同时满足）：

1. **瞬时性**（像网络抖动/对端暂不可用）  
2. **动作幂等**（整段覆盖写）  
3. **无对端终态判决**（未收到明确 reject）  
4. **本地条件未坏**（源文件仍在、磁盘/权限非确定性否决）

#### 分类表（实现错误映射时必须遵守）

**可重试** → 自动重试 → 耗尽则 `Interrupted`：

- connect 超时 / 连接暂时失败（daemon 尚在）
- 连接重置、管道断开（`ECONNRESET` / `EPIPE` 类）
- 传输中途 EOF、网络类读写错误
- 空闲超时（无进展）
- 发送侧 TCP 写出失败（网络特征）

**不可重试** → 直接 `Failed`（或 `Canceled`）：

- 对端明确拒绝（写盘失败、协议 reject）
- 磰盘满、无权限、路径非法
- 源文件丢失 / 本地读失败
- 布局错乱、帧头非法、`stream_id` 越界
- 用户取消 → `Canceled`
- 全段完成后的 **sha256 不匹配** → `Failed`（不走段续）
- **用户决策 60s 超时** → 非传输故障，不进自动重试

**灰色**：接受后立刻断连 → 先按可重试；resume 时发现槽位已无 → 转 `Failed`，禁止无限续。

裁决靠 **ErrorKind / 所处阶段**，禁止靠错误字符串匹配。

### 3.5 UI 文案（维护者：由文档作者定稿）

| 场景 | 角标 | 主文案 | 副文案 | 按钮 |
|------|------|--------|--------|------|
| 自动重试中 | 重试中 | （不改主标题） | `第 2/3 次重试流 3…` | — |
| 自动重试耗尽 | 已中断 | `传输中断，可继续` | `流 3/8 失败（连接超时）· 已完成 48% · 未完成部分将重新发送` | **继续传输** / 取消 |
| 点继续后 | 传输中 | — | — | — |
| 用户取消 | 已取消 | — | `已放弃本次传输` | — |
| 真失败 | 传输失败 | `传输失败` | 具体原因 | — |
| 系统通知（窗口隐藏） | — | `传输中断` | `「xxx.mp4」可继续，已完成 48%` | 点击 → 拉起主窗口 |

- 接收方：`收到的文件传输中断`；发送方：`发送已中断`。  
- **不用**「失败」称呼 `Interrupted`；**不用**「暂停」（易与最小化到托盘混淆），统一 **中断 / 已中断**。

### 3.6 UI 与 daemon 存活

- 「在线/离线」为**唯一真值**：whoami 轮询失败、WS 断开、进程退出都更新该真值。  
- 徽标只读真值；掉线提供 **重连 / 重启 daemon** 动作。  
- 禁止把失败 `catch (_) {}` 吞掉后仍显示已连接。

### 3.7 FFI 与手机存活

- FFI：init / shutdown **对称**，shutdown 后可再次 init（取消「只准写一次」的全局门闩）。  
- Android：传输中前台保活；进程被杀/锁屏断开 → 任务进明确失败或 `Interrupted`（若同进程内进度仍在）；**不假装仍在传**。本轮不做跨进程续传。

### 3.8 后台收尾任务

- sha256 / 保险丝 sleep **绑定任务生命周期**，完成或取消即停止，禁止裸 sleep 挂 120s。  
- 保持「传完再哈希」，避免与传输抢 IO（历史结论，勿回退为边传边哈希并发读盘）。

### 3.9 A 验收

1. 拔网线 / 杀对端 daemon / 空闲：有限时间内进入可解释终态。  
2. 一条流失败：其余流停、进度保留、UI 为「已中断」；自动重试策略生效。  
3. 点「继续传输」：只传未完成段，完成后 sha256 与现网一致通过。  
4. 点「取消」：终态 `Canceled`，资源清理。  
5. daemon 被杀：徽标与状态不再显示「已连接」。  
6. 错误分类表有单元测试锁定。
